# Paint RAG — техническое задание

## 1. Цель проекта

Разработать локальную RAG-систему для поиска и ответа на вопросы по технической документации лакокрасочных материалов.

Источники данных неоднородны:

- Excel-файлы с таблицами продуктов, цен, компонентов и расчётов;
- PDF с техническими листами продуктов;
- в будущем возможно добавление других документов.

Система должна приводить информацию к единой структуре знаний и обеспечивать точный поиск по ней.

---

В проекте уже реализованы:

- Product;
- ProductVariant;
- ProductStore;
- ProductStore.from_json();
- поиск продуктов;
- работа с артикулами;
- модели MixingRule;
- преобразование Product → Document;
- преобразование Document → Chunk;
- базовые тесты;
- базовый retriever.

Не переписывать существующую архитектуру без необходимости.

Перед изменением кода необходимо изучить:

- src/
- tests/
- data/knowledge/

и понять текущую структуру.

Все существующие тесты должны продолжать проходить.

## 4. Единая модель продукта

Продукт должен позволять хранить как структурированные, так и текстовые данные.

Минимально:

- name
- article
- technology
- aliases
- description
- application
- consumption_min
- consumption_max
- consumption_unit
- max_layers
- mixing
- variants
- technical_data
- drying
- pot_life
- source

Важно:

если конкретного поля нет в документе, НЕ придумывать значение.

Использовать null / отсутствие значения.

---

## 5. PDF

PDF-документы являются важным источником данных.

Нужно реализовать отдельный ingestion pipeline:

PDF
→ extraction
→ product identification
→ structured product
→ source metadata

PDF могут сильно отличаться по структуре.

Нельзя рассчитывать на фиксированную позицию текста.

Необходимо искать информацию по смысловым паттернам:

- Артикул
- Применение
- Рекомендуемый расход
- Количество слоёв
- Пропорции смешивания
- Отвердитель
- Разбавитель
- Время жизни смеси
- Время сушки
- Сухой остаток
- Плотность
- Вязкость
- Цвет
- Степень глянца

---

## 6. Excel

Excel уже частично импортируется существующим importer.

Не ломать существующий Excel importer.

Особенно сохранить поддержку:

- продуктов;
- вариантов;
- компонентов;
- цен;
- coverage;
- calculation_reference;
- mixing.

Если Excel и PDF описывают один и тот же продукт, система должна иметь возможность связать документы по:

1. article;
2. alias;
3. нормализованному названию.

## 7. Нормализация артикула

Артикул является главным идентификатором продукта.

Поиск должен работать для:

    PA334-9016
    PA334
    па334-9016
    PA334 9016

Нужно предусмотреть нормализацию:

- регистра;
- пробелов;
- дефисов;
- лишних символов.

Но исходное значение должно сохраняться.

---

## 8. ProductStore

ProductStore должен поддерживать минимум:

    get(name)

    get_by_article(article)

    find(query)

Поиск должен учитывать:

- article;
- name;
- aliases;
- variant article.

Необходимо избегать дублирования одного продукта.

---

## 9. Document

Document — нормализованное представление продукта для RAG.

Минимально:

    product
    variant_id
    article
    text
    metadata

Текст должен быть пригоден для semantic retrieval.

Например:

    БЕЛЫЙ ПОЛИУРЕТАНОВЫЙ 2K ГРУНТ
    Артикул: PA334-9016

    Назначение:
    ...

    Расход:
    120–140 г/м²

    Максимальное количество слоёв:
    2

    Смешивание:
    PA334-9016 — 100%
    HD816 — 33%
    Разбавитель — 15–30%

---

## 10. Chunking

Document должен разбиваться на Chunk.

Chunk должен содержать:

- id;
- text;
- product;
- variant_id;
- article;
- chunk_id.

Chunking должен быть детерминированным.

Не создавать бессмысленные чанки.

Желательно сохранять смысловые блоки:

- identification;
- application;
- mixing;
- consumption;
- drying;
- technical_data.

Если документ небольшой и целиком помещается в допустимый размер — допустим один chunk.

---

## 11. Retriever

Retriever должен уметь находить информацию по вопросам:

    Какой отвердитель у PA334-9016?

    Сколько добавлять отвердителя?

    Сколько разбавителя?

    Какой расход?

    Сколько слоёв можно наносить?

    Какое время жизни смеси?

    Какой сухой остаток?

    Какая плотность?

Retriever должен возвращать не просто текст, а результат с metadata:

- product;
- article;
- chunk;
- score;
- source.

---

## 12. Точность

Для технических параметров нельзя допускать hallucination.

Если информации нет в базе:

    "В документации нет данных об этом параметре."

Нельзя самостоятельно вычислять или придумывать характеристики без явного требования.

---

## 13. Source tracking

Каждая информация должна по возможности иметь источник.

Например:

    source:
      file: "2575-001251-200 Д-Дур лак.pdf"
      page: 1

Для Excel:

    source:
      file: ...
      sheet: Rupa
      row: 25

Это необходимо для последующего отображения источника пользователю.

---

## 14. RAG

После нормализации и chunking реализовать:

    documents
        ↓
    chunks
        ↓
    embeddings
        ↓
    vector store
        ↓
    similarity search
        ↓
    retrieved context
        ↓
    LLM

Vector store должен быть локальным.

Не использовать внешние SaaS без необходимости.

Архитектура должна позволять заменить embedding model и vector store.

---

## 15. Embeddings

Embedding должен быть вынесен за интерфейс.

Например:

    EmbeddingModel.embed(text)

Чтобы потом можно было заменить модель без изменения retriever.

---

## 16. LLM

RAG должен работать с локальной LLM.

Предпочтительно предусмотреть интерфейс:

    LLM.generate(prompt)

Конкретная модель не должна быть жёстко зашита в бизнес-логику.

---

## 17. Ответ RAG

Ответ должен основываться только на retrieved context.

Пример:

Вопрос:

    Какой отвердитель используется для PA334-9016?

Ответ:

    Для PA334-9016 используется отвердитель HD816.
    Пропорция — 33% к 100% основы.

Источник:

    PA334-9016 technical data

## 19. Ограничения

Не делать большой rewrite.

Не менять публичные API без необходимости.

Не удалять существующие тесты.

Не отключать failing tests.

Не подменять реальную реализацию mock-ами только ради прохождения тестов.

Если существующая модель противоречит новой задаче — сначала определить минимальное совместимое изменение.

---

## 20. Definition of Done

Задача считается выполненной, когда:

1. Все существующие тесты проходят.
2. Есть ingestion для PDF.
3. Есть нормализованный Product.
4. PDF и Excel могут приводиться к общей модели.
5. Product превращается в Document.
6. Document превращается в Chunk.
7. Chunk получает embedding.
8. Embeddings сохраняются в локальном vector store.
9. Retriever возвращает релевантные chunks.
10. RAG формирует ответ на основе найденного контекста.
11. Ответ содержит источник.
12. Отсутствующие данные не выдумываются.
13. Добавление нового PDF не требует изменения кода конкретно под этот продукт.
