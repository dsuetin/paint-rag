Строго по фактам из кода, данных и источников. Никаких догадок — только
подтверждённые результаты. Аудит **только диагностический**: код, данные,

## 0. Короткий вердикт

RAG индексирует **только структурированные Product-данные**
(40 продуктов из `data/knowledge/products.json` → 76 chunks).
Ни один из **методических** документов STAINWOOD (дерево, шлифовка,
растворители, подготовка, сушка, системы нанесения, детская мебель/игрушки)
**не попадает в индекс и не может быть найден retrieval'ем**.
Это не «частичное покрытие» — это **отсутствие целого класса источников**.

Три независимые причины (все подтверждены):

1. **Ingestion существует только для PDF-технокарточек**
   (`pdf_ingestion.parse_pdf_to_product`). **Парсеров `.doc`/`.docx`/`.xls`
   в коде нет вообще** — `pyproject.toml` содержит только `pydantic`,
   `pytest`, `reportlab`. 51 `.doc` + 9 `.docx` + 1 `.xls` = **61 файл
   без единой возможности извлечь текст**.
2. **Даже введённые PDF теряют методический контент**: экстрактор
   `pdf_ingestion.py` извлекает только `name / article / consumption /
   layers / mixing / technical_data` (белые списки `_TECH_FIELDS`).
   Разделы «Назначение», «Безопасность/игрушки/EN 71», «Подготовка»,
   «Шлифовка» **выбрасываются** даже у успешно введённых файлов.
3. **Сам RAG-индекс не содержит standalone-документов**:
   `indexing.build_index` вызывает `product_to_documents` **только**
   по `products.json`. Никакого пути для методических PDF/DOC/XLSX
   в `VectorStore` нет. Индекс = 76 chunks, все с `product=...`
   и `file=...ТД...`.

## 4. Код — где именно «отваливается» информация

### 4.1. Индексация — `src/paint_rag/rag/indexing.py`

```python
def build_index(product_store, embedding_model, ...):
    chunks, documents, n_products, n_documents = products_to_chunks(
        product_store.all(), chunk_size, overlap
    )
    ...
def products_to_chunks(products, ...):
    for product in products:
        docs = product_to_documents(product)   # ← только Product
        ...
```

`Document`-модель (`documents.product_to_documents`) строится **только**
от поля `Product` (name/article/variant/aliases/mixing/technicals/
compatibility/alternatives). **Никакого** `text_of(file)` / `doc_text` /
`load_markdown` / `scan_dir` — нет.

### 4.2. Pipeline — `src/paint_rag/rag/pipeline.py`

```python
store = ProductStore.from_json(products_path)
vector_store, _ = build_index(store, embedding_model)
retriever = Retriever(vector_store, embedding_model)
builder = ContextBuilder(retriever=retriever, product_store=store)
return AnswerGenerator(context_builder=builder, llm=llm, strict=strict)
```

Входные данные: **одна** `products.json`. Всё.

### 4.3. Инжест PDF — `src/importers/pdf_ingestion.py`

Whitelist-поля (строки 52-63):

```python
_TECH_FIELDS = ("gloss","dry_residue","density","viscosity",
                "pot_life","drying","shelf_life","application","usage","description")
```

Функция `parse_pdf_to_product` извлекает из PDF **только**:
`name`, `article`, `consumption`, `technology`, `max_layers`,
`mixing`, `technical_data`. Она **не** читает «Назначение», «Безопасность»,
«Подготовка», «Шлифовка», «Игрушки», «Деревянная мебель».

Следствие: даже **успешно** введённый PDF (Cetol 761) в индексе
**не несёт** строки «протестирован по DIN EN 71 часть 3 «Безопасность
игрушек»» (проверка: `игруш`=0, `EN 71`=0, `Детск`=0,
`безопасн`=0 во всех 76 chunks).

### 4.4. Coating systems — `build_relations.py` + `compatibility_resolver.py`

`scripts/build_relations.py` строит `coating_systems.json` (26 систем
по подложкам: дверь/мебель/фасад, шпон, массив, МДФ, стул, стол,
лестница, окна) и `product_relations.json`.
`systems_store.SystemsStore.from_json` читает этот файл,
`compatibility_resolver.SystemResolver` работает с ним.

**Но**: `pipeline.create_rag_pipeline` **не вызывает**
`SystemsStore.from_json` и **не передаёт** системы в
`AnswerGenerator`. `ContextBuilder`/`Retriever` работают только с
`VectorStore` (chunks из Product).

Итог: coating systems **построены, но не используются**.

### 4.5. Нет парсера для `.doc`/`.docx`/`.xls`

Глобальный поиск по `src/`, `scripts/`, `main.py`, `e2e_demo.py`:
`python-docx`, `olefile`, `win32com`, `textract`, `pandoc`, `antiword`,
`striprtf`, `lxml.*doc` — **ни одного**. `pyproject.toml`:

```toml
dependencies = ["pydantic>=2.0","pytest>=8.0","reportlab>=4.0"]
```

Следствие: **61 файл** (`.doc` × 51 + `.docx` × 9 + `.xls` × 1)
физически **невозможно** извлечь в текущем коде.

### 4.6. Нет обхода `data/STAINWOOD`

Поиск по `os.walk|rglob|glob(` в `src/`, `main.py`, `e2e_demo.py`,
`scripts/`: **только** `import_excel` (офлайн) читает
один указанный XLSX-файл + **один** PDF (из `Tехнички`) по пути
`pdf_ingestion.parse_pdf_to_product`. Никогда не сканирует
директорию.

## 10. Answer Generator + ContextBuilder — есть ли «защита»?

`ContextBuilder._query_has_unknown_code_token(...)` — **refuse**
**только** если в вопросе code-like токен (артикул/alias), который
**не совпадает** ни с одним product. Для деревянных вопросов без
артикулов (Q1–Q20 выше) этот guard **не срабатывает** и ContextBuilder
**возвращает** retrieved product-chunks (неверно по смыслу — см. §5).

`AnswerGenerator` в `paint_rag/rag/answer_generator.py:24-70`:
> «Отказ (refusal): если контекста нет (has_context=False)»

Для всех 20 вопросов `has_context=True` (есть chunks!),
поэтому LLM получает «приближённые» product-chunks и **на их
основе** может **генерировать** ответ про мебель/игрушки, **не
подтверждённый** источником. **Это и есть механизм
ложных ответов «информация не найдена» / «подойдёт любой
лак для дерева» на Task §3-5 questions.**

## ROOT CAUSE

**Одна** первичная причина (с 2 механизмами):

### Первичная причина
**RAG-индекс содержит только структурированные Product-данные
(40 продуктов из `products.json`), и НЕ содержит standalone
методические/technical документы STAINWOOD.** Это **архитектурный**
дефект: pipeline (`pipeline.py`, `indexing.py`, `documents.py`)
**принципиально** не имеет пути для `.doc`/`.docx`/XLSX/standalone-PDF
в VectorStore.

### Механизм A — Ingestion (61 файл)
**Парсеров `.doc`/`.docx`/`.xls` не существует** в `pyproject.toml`
и `src/`. 61 методический файл (дерево, шпон, МДФ, мебель, фасады,
лестницы, террасы, растворители, шлифовка, подготовка, сушка, системы
наказания, детская мебель, игрушки) **физически не может** попасть в RAG.

### Механизм B — Extractor (16 PDF + 6 Sikkens PDF с EN71)
Даже у **введённых** PDF-файлов `pdf_ingestion.py:290`
(`parse_pdf_to_product`) использует **белый список** `_TECH_FIELDS`
(gloss, dry_residue, density, viscosity, pot_life, drying, shelf_life,
application, usage, description). Поля **за его пределами**
(«Назначение», «Безопасность/игрушки/EN 71», «Подготовка», «Шлифовка»,
«Количество слоёв», «Растворители/разбавители», «Время сушки между
слоями») **выбрасываются**.

Подтверждено: `игруш=0, EN 71=0, детск=0, безопасн=0` во всех 76
indexed chunks и во `products.json` — хотя 6 PDF явно содержат
`DIN EN 71 часть 3 «Безопасность игрушек»`.

### Механизм C — Coating systems
`coating_systems.json` (26 систем по подложкам) **построен** off-line
(`scripts/build_relations.py`) но **не вызывается** runtime
(`pipeline.py:24-78`). `SystemsStore`/`SystemResolver` — dead code.

### Что НЕ является причиной
- Embedding модель (`bge-m3`) — **работает**; retrieval кос-симилярностью 0.4-0.6 — нормальная;
- Retriever/hybrid retrieval — **работает**;
- ContextBuilder — **работает** (даже отказывает при.unknown-артикуле);
- Prompt builder (rule 17+18) — **работает**;
- Лексика / русско-русский matching — **работает**;
- Векторное хранилище (JSON save/load) — **работает**.
